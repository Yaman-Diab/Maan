# أسئلة عقد الـ API — من فريق الموبايل

مرحباً 👋

بنبني طبقة الربط بتطبيق «معاً» بناءً على `collection.md`. أغلب الـ endpoints
واضحة، بس في نقاط أمثلة استجابتها `{}` فارغة بالتوثيق فما قدرنا نبني عليها.

الأسئلة مرتّبة حسب الأولوية، وحطّينا **اقتراحنا** جنب كل سؤال — لو مناسب
يكفي تردّوا «تمام» بدل ما تكتبوا العقد كامل.

---

## 1. استجابة `POST /api/auth/login` ⬅️ الأهم

التوثيق بيعرض `{}`. محتاجين نعرف بالضبط:

**أ) هل الاستجابة مغلّفة زي `/api/profile`؟**

```jsonc
// (أ‑1) مغلّفة
{ "status": 1, "message": "...", "data": { ... } }

// (أ‑2) غير مغلّفة — التوكنات بالجذر مباشرةً
{ "access": "...", "refresh": "..." }
```

> نحن حالياً بنقرأ الشكلين معاً احتياطاً، بس بدنا نثبّت واحد.

**ب) شو مفاتيح التوكنات؟**
`access` / `refresh`؟ أو `access_token` / `refresh_token`؟ أو `token` واحد؟

**ج) هل الاستجابة بترجّع كائن المستخدم؟**

- **(ج‑1)** بترجّعه → منستخدمه مباشرة ولا منعمل طلب إضافي
- **(ج‑2)** ما بترجّعه → منستدعي `GET /api/profile` بعد الدخول

> **اقتراحنا: (ج‑2)** — مصدر واحد لشكل المستخدم (`/api/profile`)، وأسهل
> عليكم بالصيانة. بس بدنا تأكيد حتى ما نفترض.

## 2. استجابة `POST /api/auth/refresh`

كمان `{}` بالتوثيق.

- شو **جسم الطلب**؟ حالياً بنبعت `{"refresh": "<token>"}` — صح؟
- شو شكل الاستجابة؟ نفس شكل `login`؟
- لما ينتهي الـ refresh token، شو رمز/كود الخطأ اللي بيرجع؟ (حتى نسجّل
  خروج المستخدم بدل ما ندخل بحلقة إعادة محاولة)

---

## 3. قيم `account_status` الكاملة

بـ`/api/profile` شفنا `"account_status": "verified"` فقط.

حسب `PROJECT_CONTEXT` في حالات: زائر → موثّق → محظور. بنينا enum على
افتراض هالقيم:

| افتراضنا | صح؟ |
|---|---|
| `pending_verification` | ؟ |
| `visitor` | ؟ |
| `verified` | ✅ مؤكّد |
| `blocked` | ؟ |

**السؤال: شو القائمة الكاملة والقيم النصية بالضبط؟**

> حالياً أي قيمة ما بنعرفها بنعاملها كـ«أقل صلاحية» (ما بتفتح الخدمات)،
> فما في خطر أمني — بس المستخدم ممكن ينحبس بلا داعي.

---

## 4. توحيد مظروف الاستجابة ⚠️

لقينا **شكلين مختلفين** للفشل بنفس الـ API:

```jsonc
{ "status": 0,       "message": "Route not found.", "errors": ["route_not_found"] }
{ "success": false,  "message": "Validation Error.", "errors": { "status.0": [...] } }
```

وكمان — الفشل بيرجع بـ **HTTP 200**.

**سؤالان:**
- في خطة لتوحيد المظروف على شكل واحد؟
- هل ممكن ترجع أكواد HTTP الحقيقية (400/401/422)؟ بيسهّل التعامل كتير
  ومعيار متعارف عليه.

> **إذا ما في نية تغيير، ما في مشكلة** — دعّمنا الشكلين، بس حابين نعرف
> حتى ما نبني على شي مؤقّت.

## 5. صيغة `birth_date`

- **الإرسال** (`register`): المثال بالتوثيق `2003/2/1` — شرطة مائلة وبلا تصفير
- **الاستجابة** (`profile`): `"birth_date": "2003-02-01"` — ISO

**هل صيغة الإرسال بالشرطة المائلة مقبولة فعلاً، أو نبعت ISO
(`2003-02-01`) بالحالتين؟**

> **اقتراحنا: ISO بالاتجاهين** — أوضح وما بيلتبس بين يوم وشهر.

---

## 6. أجسام طلبات فيها حقول تبدو منسوخة بالغلط

هالثلاثة بالتوثيق فيها حقول ما إلها علاقة بالعملية — شكلها جسم `register`
منسوخ:

| Endpoint | حقول مستغربة بالتوثيق | اللي بنبعته |
|---|---|---|
| `login` | `first_name`, `last_name`, `birth_date`, `password_confirmation`, `phone` | `email` + `password` فقط |
| `logout` | `first_name`, `password`, `fcm_token`, `role_id` | لا شي (توكن بالهيدر) |
| `forgetPassword` | `password`, `fcm_token`, `role_id` | `email` فقط |

**تأكيد: اللي بنبعته كافٍ؟** خصوصاً `logout` — بده جسم أصلاً، أو التوكن
بالهيدر بيكفي؟

## 7. `POST /api/auth/register` — الاستجابة

كمان `{}`. بعد التسجيل الناجح:

- بترجعوا جلسة (توكنات) مباشرةً، أو المستخدم لازم يسجّل دخول بعد تأكيد
  البريد؟
- الرمز بينبعت للبريد تلقائياً، أو لازم نستدعي
  `POST /api/email/verification-notification` بأنفسنا؟

---

## 8. `POST /api/auth/checkCode` — نطاق الرمز

جسم الطلب `{"code": "900482"}` بلا بريد.

**كيف بيعرف السيرفر صاحب الرمز؟** من الجلسة/التوكن؟ ولو المستخدم لسه ما
سجّل دخول (بعد التسجيل مباشرةً) — كيف بينربط الرمز فيه؟

## 9. تأكيد بسيط

`GET /api/` المسمّى «resend verification» بالتوثيق مساره ناقص. افترضنا إنه
`POST /api/email/verification-notification` (اصطلاح Laravel). صح؟
